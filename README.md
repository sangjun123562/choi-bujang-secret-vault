# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.

## 10단계: 백업 복원 및 보안 검증 절차

### 1. 사전 사본 재검증 및 안전 정책 확인 (사전 확인)
- **사본 무결성 검증**: 복원을 실행하기 전에 반드시 `data/backup-vault.json` 파일을 다시 읽어 안전 정책 사본과 저장된 해시를 검증합니다.
- **버전 및 변경 항목 사전 표시**: 복원할 버전(step: 10)과 실제 변경/복구될 항목의 범위를 실행 전에 먼저 콘솔 및 로그에 명확히 표시합니다.
- **검증 실패 시 즉각 중단**: `data/backup-vault.json` 사본 파일이 누락되었거나 해시 검증에 실패한 경우, 어떠한 복원도 수행하지 않고 즉시 작업을 중단합니다.
- **실제 운영 정책 보호**: 복구 과정에서 실제 운영 정책(src/decider.mjs 규칙, aleph.config.json의 allowedRoutes, DB 접근 통제 규칙)은 일절 임의로 건드리지 않고 원본 안전 상태를 유지합니다.

### 2. 복구 대상 및 API 경로
- **복원 대상 가상 메모 ID**: `SAMPLE_NOTE_1` (시험 계정 B의 가상 메모)
- **복구 서비스 및 경로**: `POST /api/memos` (aleph.config.json의 `restoreRoute`)
- **자료 무결성 검증**: ID, 소유자(`test_account_b`), 내용의 해시를 사본과 대조하여 변조나 삭제가 확인된 해당 한 건만 복원하며, 다른 사용자의 메모 및 감사 기록은 보존합니다.

### 3. 복구 후 1~9단계 정상·금지 요청 재시험 순서
1. **[미등록 기기 차단 검증]**: 미등록 기기의 복구 메모 조회 요청 -> `403/deny (device_not_registered)` 거부 확인
2. **[비인가 구역 차단 검증]**: 학생 계정의 공지사항 쓰기/강사 자료 접근 요청 -> `403/deny (announcements_read_only / instructor_zone_denied)` 거부 확인
3. **[메모 목록 차단 검증]**: `GET /api/memos` (전체 목록) 요청 -> `403/deny (notes_list_denied)` 거부 확인
4. **[BOLA 접근 제어 검증]**: 타 사용자 계정으로 복구된 계정 B의 메모 조회 시도 -> `403` 차단 확인
5. **[정상 단건 조회 검증]**: 계정 B의 정상 기기 세션으로 `GET /api/memos/SAMPLE_NOTE_1` 요청 -> 정상 `200` 반환 확인
6. **[폭주 공격 탐지 검증]**: 10분 내 121건 이상의 대량 GET 요청 발생 시 -> `propose_revocation (burst_read)` 탐지 발동 확인

## 11단계: 설치형 웹앱 및 기기 승인 흐름
- **PWA 설정**: `public/manifest.json`을 연결하여 설치형 웹앱 메타데이터 및 오프라인 상태 안내 UI 구현.
- **기기 보안 통제**: 단순히 앱을 설치했다는 상태만으로 기기를 신뢰하지 않으며, 서버 및 판정기의 인가 확인 전에는 자료실 목록을 절대 노출하지 않습니다.
- **비밀값 보호**: 기기 비밀키나 세션 토큰을 브라우저 로컬 저장소에 평문으로 방치하지 않고 서버 기반의 상호 서명 검증을 유지합니다.

## 12단계: 탈환 작전실 및 통합 보안 체계 운영 가이드

### 1. 시스템 아키텍처 및 엔진 출처
- **보안 엔진 출처**: 본 시스템의 접근 판정 및 위협 탐지 체계는 **ALEPH SDP 엔진**을 기반으로 설계되었습니다.
- **핵심 모듈**:
  - `src/decider.mjs`: ALEPH SDP 정책 판정 규칙(`allow_verified_device`, `deny_unregistered_device`, `stepup_risk_condition`, `block_blocked_subject`)
